# Агент аналитики Битрикс24

Консольный агент, который подключается к вашему облачному Битрикс24 и считает,
как на самом деле выглядит ваша работа: сколько задач закрыто, сколько висит и
на каких стадиях, сколько обращений в Открытых линиях обработано и за какое
время решается вопрос.

Работает на чистой стандартной библиотеке Python — внешних зависимостей нет.

## Что показывает

**Задачи**

- закрыто за период и поставлено вами;
- сколько задач не закрыто прямо сейчас и сколько из них в работе;
- разбивка по статусам (ждёт выполнения, выполняется, ждёт контроля, отложена);
- разбивка по стадиям канбана и «Моего плана», а также по проектам и группам;
- время решения задачи: среднее, медиана и 90-й перцентиль;
- нарушения сроков: просрочено сейчас, закрыто позже дедлайна, задачи без срока;
- что дольше всего висит в работе и какие задачи закрывались дольше всего.

**Открытые линии**

- обработано обращений и сколько из них закрыто;
- среднее, медианное и «худшее типичное» время решения вопроса;
- время первого ответа и соблюдение норматива (SLA);
- оценки клиентов: лайки, дизлайки, доля довольных;
- разбивка по каналам (чат на сайте, WhatsApp, Telegram и другие), по линиям и
  по часам суток с пиковой нагрузкой.

**CRM и телефония**

- выполненные дела по типам (звонки, встречи, письма);
- закрытые сделки, доля успешных, сумма и длительность цикла сделки;
- сделки в работе по стадиям;
- звонки: количество, доля состоявшихся, общая и средняя длительность.

Любой раздел можно отключить, а недоступные на вашем портале разделы агент
честно помечает и объясняет причину вместо того, чтобы показывать нули.

## Быстрый старт

### 1. Создайте входящий вебхук

В Битрикс24: **Разработчикам → Другое → Входящий вебхук**.

Отметьте права доступа (скоупы):

| Скоуп | Зачем |
| --- | --- |
| `user` | определить, чей это отчёт |
| `task` | задачи и стадии канбана |
| `imopenlines` | обращения Открытых линий |
| `crm` | дела и сделки (и запасной источник для Открытых линий) |
| `telephony` | статистика звонков |

Скопируйте адрес вида `https://ваш-портал.bitrix24.ru/rest/1/xxxxxxxxxxxx/`.

> Вебхук работает от имени создавшего его сотрудника и видит ровно то, что видит
> он. Поэтому отчёт получается персональным, а не по всей компании.

### 2. Настройте агента

```bash
cd bitrix24-agent
cp .env.example .env
# впишите B24_WEBHOOK_URL в .env
```

### 3. Проверьте подключение

```bash
python3 -m bitrix24_agent doctor
```

Команда обойдёт все источники данных и покажет, какие из них доступны:

```
Проверка доступа к порталу mycompany.bitrix24.ru
────────────────────────────────────────────────────────────────────────
  ✓ Профиль пользователя.................. user.current      доступен
  ✓ Задачи................................ tasks.task.list   доступен
  ✓ Стадии канбана........................ task.stages.get   доступен
  — Открытые линии (статистика)........... imopenlines...    метод недоступен
  ✓ CRM: дела............................. crm.activity.list доступен
```

### 4. Соберите отчёт

```bash
python3 -m bitrix24_agent report --period month --compare
```

## Команды

| Команда | Что делает |
| --- | --- |
| `doctor` | проверяет вебхук и показывает доступные источники данных |
| `report` | собирает отчёт за период |
| `ask` | отвечает на вопрос о ваших показателях (нужна настройка модели) |
| `history` | показывает сохранённые снимки отчётов |

Примеры:

```bash
# отчёт за текущий месяц в сравнении с предыдущим
python3 -m bitrix24_agent report --period month --compare

# только задачи и Открытые линии за прошлую неделю
python3 -m bitrix24_agent report --period last-week --sections tasks,openlines

# июнь 2026 года в Markdown, в файл
python3 -m bitrix24_agent report --period 2026-06 --format markdown --output june.md

# машиночитаемый JSON — для дашборда или собственной обработки
python3 -m bitrix24_agent report --period 30d --format json

# снимок в историю, чтобы потом сравнивать запуски
python3 -m bitrix24_agent report --period week --save
python3 -m bitrix24_agent history
```

### Периоды

`today`, `yesterday`, `week`, `last-week`, `month`, `last-month`, `quarter`,
`year`, `all`, а также `30d` (последние N дней), `2026-06` (конкретный месяц),
`2026-06-01` (день) и `2026-06-01..2026-06-30` (произвольный интервал).
Русские синонимы (`сегодня`, `неделя`, `месяц`, `квартал`, `год`) тоже работают.

Ключ `--compare` добавляет к каждому показателю изменение относительно
предыдущего периода такой же длины. Рост помечается стрелкой, а ухудшение —
знаком `⚠`: рост числа закрытых задач это хорошо, а рост просрочек — нет.

### Вопросы на естественном языке

Если в `.env` заданы `B24_LLM_BASE_URL`, `B24_LLM_API_KEY` и `B24_LLM_MODEL`,
можно спрашивать про свои же цифры:

```bash
python3 -m bitrix24_agent ask "На что у меня уходит больше всего времени?" --period 30d
```

Агент собирает отчёт, отдаёт модели готовый JSON с показателями и просит
отвечать только по этим числам. Без настройки модели остальные команды
работают как обычно.

## Запуск по расписанию

Еженедельный отчёт каждый понедельник в 9 утра (cron):

```cron
0 9 * * 1 cd /path/to/bitrix24-agent && /usr/bin/python3 -m bitrix24_agent report \
    --period last-week --save --format markdown --output reports/$(date +\%Y-\%m-\%d).md
```

На Windows то же самое делается через «Планировщик заданий» с действием
`python -m bitrix24_agent report --period last-week --save`.

## Как это устроено

```
bitrix24_agent/
  transport.py     HTTP к вебхуку: лимит частоты, повторы, разбор ошибок портала
  client.py        REST-клиент: пагинация, batch до 50 команд, счётчики по total
  period.py        разбор периодов с учётом часового пояса портала
  normalize.py     приведение полей: портал отвечает и camelCase, и UPPER_CASE
  metrics.py       среднее, медиана, перцентили и форматирование по-русски
  collectors/      сбор данных по разделам (задачи, линии, CRM, телефония)
  agent.py         оркестратор: собирает разделы в один отчёт
  report.py        вывод в текст, Markdown и JSON
  storage.py       история снимков в SQLite
  llm.py           необязательный слой вопросов на естественном языке
```

Три решения, которые определяют поведение агента:

**Счётчики отдельно от выборки.** Количество задач берётся из поля `total`
списочного метода — это один запрос независимо от объёма. Детальные метрики
(время решения, стадии, просрочки) считаются по выгруженным записям с лимитом
`B24_MAX_TASKS`. Если выборка упёрлась в лимит, отчёт помечается как неполный:
счётчики остаются точными, а средние честно подписаны как посчитанные по части
данных.

**Медиана рядом со средним.** Одна забытая на два месяца задача сдвигает среднее
так, что оно перестаёт описывать реальность. Медиана показывает типичный случай,
а 90-й перцентиль — насколько плох «плохой» случай.

**Падение раздела не роняет отчёт.** Нет модуля телефонии, закрыт скоуп CRM, не
доехало обновление Открытых линий — соответствующий раздел помечается и
объясняет причину, остальные собираются как обычно.

## Используемые методы REST

| Раздел | Метод | Назначение |
| --- | --- | --- |
| Задачи | `tasks.task.list` | задачи по исполнителю, статусу и датам |
| Задачи | `task.stages.get` | стадии канбана и «Моего плана» |
| Задачи | `sonet_group.get` | названия проектов и групп |
| Открытые линии | `imopenlines.v2.Session.list` | сессии с метриками ожидания и оценками |
| Открытые линии | `imopenlines.config.list.get` | названия линий |
| Открытые линии | `crm.activity.list` | запасной источник, если статистика недоступна |
| CRM | `crm.activity.list`, `crm.deal.list`, `crm.status.list` | дела, сделки, названия стадий |
| Телефония | `voximplant.statistic.get` | статистика звонков |
| Общее | `user.current`, `user.get`, `batch` | профиль и пакетные запросы |

## Особенности и ограничения

**Статистика Открытых линий раскатывается постепенно.** Методы `imopenlines.v2.*`
появились в обновлении `imopenlines 26.700.0` и требуют права
`report_open_lines` (зависит от тарифа). Пока обновление не приехало на портал,
метод отвечает `METHOD_NOT_YET_AVAILABLE`, и агент переключается на подсчёт по
делам CRM с пометкой «приблизительно»: там видно количество обращений и
оценочное время решения, но нет оценок клиентов и времени первого ответа.
Проверить состояние портала можно командой `doctor`.

**Лимит интенсивности.** Облако разрешает 2 запроса в секунду (Enterprise — 5).
Агент сам выдерживает интервал, объединяет счётчики в `batch` и повторяет запрос
с нарастающей паузой при ошибке `QUERY_LIMIT_EXCEEDED`. Полный отчёт за месяц
обычно укладывается в два-три десятка запросов.

**Время решения задачи** считается как разница между постановкой и закрытием, а
не как фактически затраченное время. Списанное по таймеру время показывается
отдельной строкой.

**Чужая статистика.** Ключ `--user` покажет отчёт по другому сотруднику, но
только если у владельца вебхука есть права видеть его задачи и обращения.

## Разработка

```bash
python3 -m unittest discover -s tests -t .
```

Тесты работают на фейковом портале, который повторяет поведение настоящего REST:
фильтры, страницы по 50 записей, `total`/`next` в конверте и разбор команд внутри
`batch`. Сеть при этом не нужна.
